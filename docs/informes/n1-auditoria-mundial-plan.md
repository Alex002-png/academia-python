## 3. Cajas "Truco de experto" a insertar (las mejores, sin duplicar)

Regla anti-duplicación: `enumerate`, `zip`, `Counter`, `defaultdict`, `deque`, star-unpacking y prefix-sums aparecen en varias auditorías. **Se enseñan UNA vez en su módulo natural** y los demás módulos solo los *usan* (ya no como truco).

**M1 — Fundamentos**
- `dict(zip(claves, valores))` — construir dict de listas paralelas sin índices *(idiom oficial; Fluent Python)*
- `enumerate(seq, start=1)` — índice+valor sin `range(len)` *(PEP 279; MIT 6.0001/CS50P)*
- `Counter(...).most_common(n)` — frecuencias en 1 línea *(stdlib collections)*
- `es_primo` con `all(n%i for i in range(2, int(n**0.5)+1))` — O(√n) + short-circuit *(teoría de números clásica)*
- `defaultdict(list)` — agrupar sin comprobar clave *(stdlib collections)*
- `f'{variable=}'` — debug autodocumentado *(CPython 3.8)*

**M2 — OOP**
- `@dataclass(frozen=True, order=True)` — genera `__init__`/`__repr__`/`__eq__`/`__hash__` *(PEP 557; Fluent Python)*
- Idiom canónico de `__repr__`: `type(self).__name__` + `!r` *(Fluent Python cap.1)*
- `return NotImplemented` en `__eq__` (no `False`) *(modelo de datos Python)*
- `@functools.total_ordering` — deriva 3 operadores de comparación *(functools, Hettinger)*
- Constructor alternativo `@classmethod ... return cls(...)` *(stdlib: `datetime.fromtimestamp`)*
- `__slots__` — memoria + caza typos de atributo *(modelo de datos)*

**M3 — Algoritmos**
- `deque.popleft()` para la cola de BFS — O(1) vs O(n) *(docs collections)* ← **cierra la contradicción 0.1**
- `@cache`/`@lru_cache` — memoización en 1 línea *(functools)*
- `bisect_left`/`bisect_right` — lower/upper bound sin off-by-one *(stdlib bisect)*
- Algoritmo de **Kadane** — máx subarreglo en O(n) *(Jay Kadane, CMU)*
- Sumas prefijas + `itertools.accumulate` *(competitive programming)*
- Patrón Dijkstra: heap de `(prioridad, item)` + `heapify` O(n) + `nlargest` *(heapq)*

**M4 — Git**
- `git commit --amend --no-edit` — arreglar el último commit *(Pro Git 2.4)*
- `git add -p` — commits atómicos trozo a trozo *(Missing Semester)*
- `git reflog` — recuperar commits "perdidos" *(Pro Git 7.10)*
- `git switch`/`git restore` — verbos claros vs `checkout` sobrecargado *(Git 2.23)*
- Alias `lg = log --oneline --graph --decorate --all` *(Pro Git 2.7)*

**M5 — Terminal/procesos**
- `python -m modulo` (`-m venv`, `-m http.server`, `-m pip`) — usa SIEMPRE el intérprete activo *(PEP 338)*
- `sys.executable` / `os.getpid()` — en qué Python/proceso estoy, sin adivinar *(stdlib)*
- `subprocess.run([lista])` (shell=False) — el word-splitting no existe por diseño *(docs subprocess)*
- `set -euo pipefail` + `IFS=$'\n\t'` — modo estricto de Bash *(Aaron Maxwell)*
- Manejar `SIGTERM` con `signal` (y SIGKILL NO se captura) *(POSIX/TLPI)*
- `!!` / `sudo !!` / `!$` / Ctrl-R / `cd -` — historial y navegación *(Missing Semester)*

**M6 — Redes/APIs**
- Las 2 líneas obligatorias: `timeout=` en cada petición + `raise_for_status()` *(docs requests)*
- `requests.Session()` con pool de conexiones (keep-alive) *(docs requests)*
- Full Jitter: `random.uniform(0, min(cap, base*2**intento))` *(Marc Brooker, AWS 2015)* ← **cierra 0.4**
- `status // 100` o `http.HTTPStatus(...).is_client_error` — clasificar sin escaleras de rango *(stdlib http)*
- Idempotency key con `uuid.uuid4()`, misma en todos los reintentos *(docs Stripe)*

**M7 — Bases de datos**
- `with con:` — commit/rollback transaccional automático *(docs sqlite3)*
- `con.row_factory = sqlite3.Row` — acceso por nombre, no `fila[1]` *(docs sqlite3)*
- UPSERT `INSERT ... ON CONFLICT DO UPDATE SET x = excluded.x` *(SQLite 3.24)*
- Anti-join `LEFT JOIN ... WHERE b.id IS NULL` — filas sin pareja *(patrón estándar; conecta con el gotcha FK de T6)*
- Duplicados `GROUP BY col HAVING COUNT(*)>1` *(auditoría de datos)*
- Regla del prefijo izquierdo en índice compuesto *(Use The Index, Luke)*
- Inserción masiva en UNA transacción (fsync por commit → 100-1000× más rápido) *(SQLite FAQ)*

Sin embargo hay CUATRO huecos concretos que impiden decir "podría competir con el mejor curso del mundo": (1) los heaps/colas de prioridad NUNCA se enseñan pese a usarse en Dijkstra —contradice el propio principio de "abrir la caja" que sí se aplica a hash; (2) Ordenación (T3) nunca enseña un algoritmo O(n log n) ni el paradigma divide-y-vencerás (merge sort), el mismo que el recurso citado (6.006 L12) sí cubre; (3) BFS exige `list.pop(0)` en un ejercicio CALIFICADO, volviéndolo O(V²) y contradiciendo directamente lo que T4 enseñó sobre pop(0); (4) faltan sumas prefijas y los idioms pythonicos profesionales (lru_cache, Counter, defaultdict, deque) como "versión profesional" tras la manual, que la métrica 5 del estándar exige. Son gaps reales, no inventados, y todos de alto valor y bajo costo de corrección.

**Gaps:**

- [alta] **T9 Grafos (Dijkstra, Día 44) + estructura ausente en todo M3** — El heap binario / cola de prioridad nunca se enseña como estructura de datos. `heapq.heappush/heappop` se usa como caja negra en Dijkstra sin explicar qué es un montículo, por qué heapify es O(n), por qué push/pop son O(log n), ni cómo se representa con un array. El módulo SÍ 'abre la caja' de las tablas hash (T8 construye una desde cero) pero deja el heap como magia. _(por que: MIT 6.006 dedica una lección entera a Heaps y Heapsort; CS61B y CLRS (cap. 6) también. Es una de las estructuras fundamentales. Enseñar Dijkstra con un heap opaco, en un curso que en el tema contiguo insiste en no tratar estructuras como cajas negras, es una inconsistencia pedagógica real. Un alumno no podría explicar en una entrevista por qué Dijkstra es O((V+E)log V).)_
- [alta] **T3 Ordenación (Días 29-30)** — Nunca se enseña un algoritmo de ordenación O(n log n) ni el paradigma divide-y-vencerás. El tema cubre bubble y insertion (ambos O(n²)) escritos a mano, y `sorted()` como caja negra, pero el salto de O(n²) a O(n log n) —el concepto central de por qué ordenar es 'barato'— nunca se materializa. El propio recurso citado (MIT 6.006 Lecture 12, y el motivo dice 'cubre bubble/selection/merge sort') incluye merge sort, pero el contenido no. _(por que: Merge sort es el ejemplo canónico de divide-y-vencerás en CLRS cap. 2 y refuerza directamente T5 (Recursión). Sin él, el alumno cree que ordenar rápido es 'magia de sorted()' y no entiende la recurrencia T(n)=2T(n/2)+O(n). Es el puente conceptual perdido entre recursión y eficiencia.)_
- [alta] **T9 Grafos BFS (Día 41, ejercicio n1m3t9e2 y todos los labs)** — BFS se implementa con `cola = [inicio]` y `cola.pop(0)`, y el check del ejercicio calificado RECHAZA cualquier solución que no use `.pop(0)`. `list.pop(0)` es O(n), por lo que el BFS enseñado es O(V²) en vez de O(V+E). Contradice directamente T4 (Día 31, ejercicio 'De lista+pop(0) a deque' + el hist que cita las Python docs sobre por qué pop(0) es O(n)). No hay ni una nota de que en producción se use `collections.deque.popleft()`. _(por que: Es una contradicción interna verificable: el mismo módulo enseña que pop(0) es un antipatrón O(n) y luego lo exige en un ejercicio calificado. Cualquier practicante de competitive programming o entrevistador lo marcaría. Rompe la métrica 9 (trade-offs honestos) y la coherencia del módulo.)_
- [media] **T6 Patrones / T1 Big-O — técnica ausente** — No se enseñan las sumas prefijas (prefix sums / `itertools.accumulate`): precomputar acumulados para responder suma-de-rango en O(1) tras O(n). Complementa de forma natural la ventana deslizante de T6 y el conteo de pares. _(por que: Es, literalmente, la primera técnica del repertorio de competitive programming (USACO/Codeforces/ICPC) y aparece en incontables problemas de entrevista. Su ausencia deja incompleto el 'llavero de patrones' que T6 promete.)_
- [media] **T8 Tablas hash (Días 39-40)** — Solo se enseña resolución de colisiones por encadenamiento (chaining). No se menciona el direccionamiento abierto (open addressing / probing lineal), que es EXACTAMENTE lo que usa el `dict` de CPython. La afirmación 'abres la caja de cómo dict logra O(1)' es pedagógicamente valiosa pero técnicamente imprecisa: el modelo mostrado no es el que Python usa. _(por que: CS50, CLRS (cap. 11) y cualquier curso serio presentan ambas estrategias comparadas (métrica 8: comparar alternativas). Para el estándar 'válido dentro de 2-3 años y aprobado por un senior sin reservas', afirmar que un dict funciona por chaining cuando CPython usa open addressing es un error de exactitud que un ingeniero senior objetaría.)_
- [media] **Todo M3 — métrica 5 (código profesional además del desde-cero)** — El módulo enseña muy bien las versiones 'desde cero' (memo=None manual, setdefault para adyacencia, dict.get para frecuencias) pero nunca muestra la 'versión profesional' pythonica equivalente para comparar: `functools.lru_cache`/`@cache` (memoización en 1 línea), `collections.Counter` (frecuencias), `collections.defaultdict` (adyacencia), `collections.deque` (colas). La métrica 5 del estándar exige explícitamente comparar la versión desde-cero con la profesional. _(por que: Un alumno que solo conoce la versión manual reinventa a mano lo que la stdlib ya resuelve idiomáticamente —justo el antipatrón que T3 critica ('¿cuándo reimplementarías algo que la librería hace mejor?'). Mostrar ambas cierra el círculo y es lo que se espera en revisión de código real.)_
- [baja] **T7 Árboles (Días 37-38)** — No hay recorrido por niveles (level-order / BFS sobre el árbol) explícito, pese a que T9 introduce BFS pocos días después —conectarlos sería natural. Tampoco se nombra el concepto de 'componentes conexas' en grafos (el lab 'todas_alcanzables' lo roza sin nombrarlo). _(por que: El recorrido por niveles es uno de los cuatro recorridos canónicos de árbol en cualquier curso; nombrar 'componentes conexas' da vocabulario transferible. Son huecos menores frente a lo ya cubierto, pero pulen la completitud.)_

**Trucos de experto a agregar:**

- **Sumas prefijas (prefix sums): precomputa un array de acumulados una vez, y luego cualquier suma de rango nums[i..j] se responde en O(1) como pref[j+1]-pref[i].** _(Competitive programming (USACO/Codeforces/ICPC); en Python el equivalente idiomático es itertools.accumulate. Es la técnica #1 del repertorio de rango.)_ — Convierte q consultas de suma de rango de O(n) cada una a O(1) cada una tras O(n) de preproceso: de O(n·q) a O(n+q). Complementa la ventana deslizante que T6 ya enseña.
- **@lru_cache / @cache: memoización profesional en una sola línea, sin gestionar el diccionario memo a mano.** _(Biblioteca estándar de Python (functools). @cache (3.9+) es azúcar de @lru_cache(maxsize=None). Es la forma pythonica que un senior espera ver tras entender la versión manual.)_ — Elimina toda la fontanería de memo=None/if n in memo, evita el bug del valor por defecto mutable que el propio T5 advierte, y deja la recurrencia pura y legible. Muestra la 'versión profesional' que la métrica 5 exige comparar con la manual.
- **collections.deque.popleft() para la cola de BFS en vez de list.pop(0): O(1) en lugar de O(n).** _(Documentación oficial de Python (collections.deque) y práctica universal de competitive programming. Corrige el antipatrón que el propio módulo enseña a evitar en T4.)_ — Con list.pop(0) el BFS del módulo es O(V²); con deque.popleft() es el O(V+E) correcto. Es exactamente la lección de T4 aplicada donde de verdad importa, y hace que el BFS escale a grafos grandes reales.
- **collections.Counter para frecuencias y collections.defaultdict(list) para listas de adyacencia: reemplazan el patrón manual dict.get(x,0)+1 y setdefault.** _(Biblioteca estándar de Python (collections). defaultdict/Counter son los idioms canónicos que aparecen en toda solución profesional de entrevista.)_ — Counter cuenta frecuencias en una línea y trae .most_common(k); defaultdict elimina la verbosidad de setdefault en cada arista. Menos código, menos bugs, y es la versión que un revisor senior espera junto a la manual.
- **bisect.bisect_left / bisect_right: el lower_bound/upper_bound de C++ STL, ya optimizado en C. bisect_left da el primer indice >= x; bisect_right, el primero > x.** _(Biblioteca estándar de Python (bisect); espeja directamente std::lower_bound/upper_bound de C++ STL, herramienta base en competitive programming. El módulo ya menciona bisect de pasada en T2 pero no enseña el idiom lower/upper bound.)_ — Da búsqueda binaria correcta (sin off-by-one, el bug que T2 destaca) en una línea, y resuelve 'cuántos elementos < x', 'primer elemento >= x' e insertar-manteniendo-orden sin reimplementar los límites a mano.
- **Algoritmo de Kadane: máxima suma de subarreglo contiguo en O(n) con una sola variable de estado (extender la ventana actual o reiniciar en el elemento actual).** _(Jay Kadane (Carnegie Mellon). Es el ejemplo canónico de 'DP de una dimensión disfrazada' y aparece en casi toda ronda de entrevista de arrays.)_ — Resuelve en O(n) y O(1) espacio un problema que en fuerza bruta es O(n²) o O(n³); es el puente perfecto entre la ventana deslizante de T6 y la subestructura óptima de T10, mostrando que una recurrencia de DP puede colapsar a dos variables.
- **heapq.heapify (montículo en O(n) in-place), heapq.nlargest/nsmallest (top-k en O(n log k)) y el patrón de tupla (prioridad, item) con borrado perezoso.** _(Biblioteca estándar de Python (heapq). El patrón (prioridad, item) + 'saltar si ya visitado' es el estándar de Dijkstra en competitive programming; nlargest/heapify son idioms de selección top-k.)_ — Da la extracción del mínimo/máximo en O(log n) que Dijkstra necesita, y top-k sin ordenar todo (O(n log k) en vez de O(n log n)). Hace explícita la estructura que hoy el módulo usa a ciegas, respondiendo por qué Dijkstra es O((V+E)log V).

**Temas nuevos sugeridos:**

- **Montículos (heaps) y colas de prioridad — construir un heap binario desde cero antes de usar heapq** — Es el hueco más grave: T9 usa heapq en Dijkstra como caja negra mientras T8 sí 'abre la caja' de las tablas hash. Un tema de 2 días (representar un heap con array, sift-up/sift-down, heapify O(n), heappush/heappop O(log n), y heapsort) cierra la incoherencia y da la base para entender por qué Dijkstra es O((V+E)log V). Debería ir ANTES de T9.d4 (Dijkstra). _(fuente: MIT 6.006 Lecture 4 'Heaps and Heap Sort'; CLRS cap. 6 'Heapsort'; Berkeley CS61B (Priority Queues / Heaps).)_
- **Merge sort y el paradigma divide-y-vencerás** — T3 solo enseña ordenaciones O(n²) a mano y sorted() como caja negra; nunca se materializa cómo se logra O(n log n). Merge sort es el ejemplo canónico de divide-y-vencerás, refuerza directamente T5 (Recursión) con la recurrencia T(n)=2T(n/2)+O(n), y el recurso ya citado (6.006 L12) lo cubre. Encaja como Parte 3 de T3 o entre T3 y T5. _(fuente: CLRS cap. 2.3 'Designing algorithms / Merge sort'; MIT 6.006 Lecture 3; Berkeley CS61B (Merge Sort).)_
- **Sumas prefijas y arrays de diferencias** — Técnica fundacional de competitive programming ausente por completo, que complementa la ventana deslizante de T6 y el conteo de pares. Un tema corto (A, 3 días) sobre prefix sums 1D/2D y difference arrays da herramientas de consulta de rango en O(1) que reaparecen en todo problema real de arrays. _(fuente: Competitive Programmer's Handbook (Antti Laaksonen), cap. 'Range queries'; USACO Guide (Prefix Sums); CP-Algorithms (e-maxx, prefix sums).)_
- **Union-Find (conjuntos disjuntos / DSU) con compresión de caminos y unión por rango** — Hueco conceptual real en T9: componentes conexas y detección de ciclos en grafos NO dirigidos se resuelven de forma casi O(1) amortizado con DSU, y el lab 'todas_alcanzables' roza el concepto sin nombrarlo. Es también el prerequisito de Kruskal (MST). Opcional/avanzado dentro de N1, pero es un estándar de la referencia mundial. _(fuente: CLRS cap. 21 'Data Structures for Disjoint Sets'; competitive programming (CP-Algorithms, DSU); Princeton/Sedgewick Algorithms (Union-Find).)_

### N1-M4 (Computer Science / Git — Laboratorios 5-8, modalidad real labs)

**Veredicto:** necesita-trabajo

Modulo solido y muy por encima de la media: alinea explicitamente con Pro Git y Missing Semester (MIT), y ya incluye contenido que la mayoria de cursos "de Git basico" omite — rebase interactivo (squash), stash, blame y bisect (incluido bisect run), reglas de commit de Beams + Conventional Commits, flujo de Pull Request con las tres respuestas oficiales de GitHub, y el criterio de tamano de cambio de Google (Small CLs). Los diagnosticos de error son reales y reproducibles, y la regla "nunca reescribas historia compartida" esta bien tratada. Sin embargo, para un alumno DESDE CERO faltan tres capitulos fundacionales que Pro Git enseña ANTES de ramas (cap. 2.2 y 2.4) y que en la practica son la causa numero uno de accidentes: (1) .gitignore — critico en Python, hoy el alumno subira __pycache__/ y, peor, un .env con secretos, y el modulo dice "nunca subas claves" sin enseñar el mecanismo para evitarlo; (2) git diff / git diff --staged — el alumno hace commit a ciegas, sin inspeccionar que va a fotografiar; (3) deshacer (git restore/--staged, git reset, git commit --amend, git revert) — la necesidad numero uno de un principiante. Tambien falta el "lado de bajada" de Git colaborativo (git clone/fetch/pull) pese a que el modulo enseña PRs. Son huecos ADITIVOS, no correcciones: el contenido presente es correcto. Con una quinta lección de "Inspeccionar y deshacer + .gitignore" y añadir pull/clone, el modulo queda a nivel mundial.

**Gaps:**

- [alta] **n1m4t1 Fundamentos y primer repositorio** — .gitignore no aparece en NINGUNA de las 4 lecciones. No se enseña a crear un .gitignore ni el concepto de archivo ignorado/rastreado. En un proyecto Python esto significa que el alumno subira __pycache__/, *.pyc, .venv/ y — el riesgo real — un archivo .env con claves. El propio modulo lista 'Nunca subir contraseñas o claves reales' como buena practica pero no enseña el unico mecanismo que lo previene. _(por que: Es contenido fundacional de Pro Git cap. 2.2 (Recording Changes), enseñado ANTES de ramas. Sin el, la buena practica de seguridad que el modulo predica es inaplicable y el primer repo publico del alumno filtra basura o secretos. Un ingeniero senior lo rechazaria de inmediato (pregunta de aceptacion 2 de DOC-STD-01).)_
- [alta] **n1m4t1 / n1m4t2 (flujo diario)** — git diff y git diff --staged. El alumno pasa de editar a 'git add' y 'git commit' sin ninguna herramienta para VER que cambio. No hay forma enseñada de revisar el cambio antes de fotografiarlo. _(por que: Pro Git cap. 2.2 trata git diff como parte del ciclo basico de trabajo, no como avanzado. Inspeccionar antes de commitear es lo que hace posible un commit atomico real (objetivo explicito de L5) y evita el clasico 'commiteé algo que no queria'. Sin diff, 'commit atomico' se vuelve un acto de fe.)_
- [alta] **n1m4t2 Ramas y merge (o lección nueva)** — Deshacer / corregir errores: git restore <archivo> (descartar cambios), git restore --staged (quitar de staging), git commit --amend (arreglar el ultimo commit), git reset, y git revert (deshacer un commit ya publicado sin reescribir historia). Solo aparece 'git checkout -- archivo' de pasada dentro de un diagnostico, sin enseñarse. _(por que: Pro Git cap. 2.4 'Undoing Things' es material fundacional para principiantes y es, empiricamente, lo que un alumno desde cero mas necesita (todos rompen algo el primer dia). El modulo enseña a reescribir historia (rebase) pero no lo mas basico: como salir de un error comun sin panico. Es un hueco conceptual, no de relleno.)_
- [media] **n1m4t3 El flujo Pull Request** — El lado de 'bajada' del Git colaborativo: git clone (solo se menciona al pasar en L8), git fetch y git pull para sincronizar main antes de ramificar y antes de abrir un PR. Todo el modulo sube (push) pero nunca baja/sincroniza; el PR se hace y se auto-fusiona sin nadie mas. _(por que: Pro Git cap. 2.5 y 3 tratan fetch/pull como parte del ciclo colaborativo. Enseñar PRs sin enseñar a sincronizar con el remoto deja al alumno indefenso ante el escenario mas comun en equipo: 'tu rama esta desactualizada respecto a main'. Es incoherente enseñar la colaboracion (PR) sin su prerequisito (traer cambios ajenos).)_
- [media] **n1m4t3 El flujo Pull Request** — El flujo fork + upstream. El PR se practica solo sobre el propio repo (subes tu rama y te auto-fusionas). La contribucion real de open source — que el contexto de la lección invoca ('parches de comunidades open source', 'PR ajeno') — es fork del repo de otro, remote 'upstream', PR contra el original. _(por que: El modelo fork-and-PR es LA forma en que se contribuye a proyectos ajenos en GitHub; sin el, el alumno cree que un PR solo aplica a repos propios. GitHub Docs lo documenta como flujo estandar. Es el eslabon que conecta 'revisar un PR ajeno' con 'proponer un cambio a un proyecto que no es mio'.)_
- [media] **n1m4t1 Autenticacion** — Configuracion guiada de autenticacion (Personal Access Token o clave SSH) como paso, no solo como diagnostico reactivo tras el fallo. Tambien falta el 'git config --global user.name/user.email' inicial obligatorio. _(por que: El fallo de autenticacion en el primer push es universal y bloqueante para un alumno desde cero; hoy solo se aborda cuando ya fallo. Y sin user.name/user.email configurados, el primer commit falla o queda con autor incorrecto — es literalmente lo primero que exige Pro Git cap. 1.6 (First-Time Git Setup).)_

**Trucos de experto a agregar:**

- **git commit --amend --no-edit para añadir un archivo olvidado o arreglar el ultimo commit SIN crear un commit extra 'arreglos'.** _(Idiom universal de industria; documentado en Pro Git cap. 2.4 'Undoing Things'.)_ — El alumno desde cero olvida constantemente un archivo o deja un typo en el mensaje. En vez de ensuciar la historia con 'fix', 'fix2', reincorpora al mismo commit — refuerza directamente el objetivo de 'commits atomicos y limpios' que ya predica L5. Regla: solo sobre commits AUN no publicados (misma regla que ya enseña el modulo para rebase).
- **git add -p (modo parche): confirma trozo por trozo (hunk) de un mismo archivo, respondiendo y/n a cada bloque, en vez de 'git add .' entero.** _(Ejercicio explicito de Missing Semester (MIT), Version Control; funcion nativa de Git.)_ — Es la herramienta que hace POSIBLE el commit atomico real que el modulo exige: si tocaste dos cosas distintas en un archivo, add -p te deja separarlas en dos commits limpios. Convierte 'commit atomico' de consejo abstracto en accion concreta.
- **git reflog: registro de TODO adonde apunto HEAD (incluye commits 'perdidos' tras un reset/rebase/amend). Permite recuperar trabajo que parecia borrado.** _(Pro Git cap. 7.10 'Rewriting History' / Data Recovery; citado en Missing Semester como salvavidas.)_ — El modulo enseña rebase interactivo (reescribir historia), que es donde los principiantes mas se asustan de 'perder' commits. reflog es la prueba de que en Git casi nada se pierde de verdad — reduce el miedo y da un plan de recuperacion real, en linea con la filosofia 'un conflicto no es catastrofe' del modulo.
- **git switch (cambiar/crear ramas) y git restore (descartar cambios) — introducidos en Git 2.23 (2019) para separar dos usos confusos del viejo git checkout.** _(Documentacion oficial de Git 2.23; recomendacion de git-scm y GitHub para principiantes.)_ — El modulo usa 'git checkout -b' y 'git checkout -- archivo': el mismo verbo para dos cosas totalmente distintas (moverse entre ramas vs. tirar cambios) confunde a quien empieza. switch/restore tienen nombres que dicen lo que hacen — menos errores de 'checkout accidental'. Vale enseñar ambos (el alumno vera checkout en repos viejos).
- **Alias de Git para un log grafico legible: git config --global alias.lg "log --oneline --graph --decorate --all".** _(Pro Git cap. 2.7 'Git Aliases'; patron omnipresente en dotfiles de ingenieros.)_ — L8 solo enseña 'git log --oneline' (lista plana) — el alumno no VE las ramas ni los merges. --graph --all dibuja el arbol de ramas en ASCII, haciendo visible el modelo mental de 'puntero movil' de L6. Ademas enseña el habito de personalizar Git con alias, que todo practicante de elite tiene.
- **Plantilla oficial GitHub para Python + gitignore global: git config --global core.excludesFile ~/.gitignore_global para ignorar basura de tu editor en TODOS tus repos, y usar el Python.gitignore de github/gitignore por proyecto.** _(Repositorio oficial github/gitignore (plantillas mantenidas por GitHub); Pro Git cap. 2.2.)_ — Cierra el gap critico de seguridad/limpieza: evita subir __pycache__/, .venv/ y — clave — .env con secretos. El gitignore global evita repetir reglas de editor (.DS_Store, .idea/) en cada repo. Es la practica exacta que usan los equipos reales, no una regla inventada.

**Temas nuevos sugeridos:**

- **Laboratorio nuevo: Inspeccionar y deshacer — git diff, .gitignore y el arte de arreglar errores** — Cubre de una sola vez los tres gaps de severidad alta (diff, .gitignore, deshacer). Es el capitulo que Pro Git enseña ANTES de ramas y que hoy el modulo salta. Contenido concreto sin relleno: (1) git diff / --staged para ver antes de commitear; (2) crear un .gitignore de Python y demostrar que un .env deja de rastrearse (con el error real de un secreto ya commiteado y como se saca con git rm --cached); (3) deshacer con git restore, git restore --staged, git commit --amend, y git revert para un commit ya publicado. Encaja perfecto entre L5 y L6 y mantiene la modalidad real labs (error en vivo: commitear un .env por accidente y recuperarse). _(fuente: Pro Git cap. 2.2 (Recording Changes / Ignoring Files) y cap. 2.4 (Undoing Things); Missing Semester MIT, seccion de staging y recuperacion.)_
- **Ampliar Laboratorio 7 con clone / fetch / pull y el flujo fork + upstream** — El modulo enseña a PROPONER cambios (push, PR) pero nunca a TRAER cambios (clone/fetch/pull) ni a contribuir a un repo ajeno (fork/upstream), que es el escenario real que su propio contexto invoca ('parches de open source', 'PR ajeno'). No es tema nuevo desde cero sino completar el ciclo colaborativo ya iniciado: sincronizar tu main con el remoto, hacer fork de un repo real, remote upstream, y abrir un PR contra el original. Es lo que separa 'PR en mi repo' de 'contribuir a un proyecto de verdad'. _(fuente: Pro Git cap. 2.5 (Working with Remotes) y cap. 6.2 (Contributing to a Project / fork); GitHub Docs 'About forks' y 'Syncing a fork'.)_

### N1 · M5 — Entorno real: terminal, procesos, memoria/permisos, automatización (labs n1m5t1..t5)

**Veredicto:** necesita-trabajo

**Trucos de experto a agregar:**

- **El idiom `python -m modulo` en vez de invocar scripts o binarios sueltos: `python -m venv .venv`, `python -m http.server 8000`, `python -m json.tool datos.json`, `python -m pdb prog.py`. Garantiza que se usa el intérprete (y su entorno) exacto que tienes activo, sin depender de dónde viva un ejecutable en el PATH.** _(PEP 338 / documentación oficial de CPython; convención universal en la industria Python (Django, pip, pytest se invocan así).)_ — Elimina de raíz la confusión de T4/venv 'instalé pero no está': `python -m pip install X` siempre instala en el MISMO Python cuyo `python` acabas de escribir, aunque el PATH apunte a otro pip. En tiempo de ejecución evita el error #1 del módulo de entornos virtuales.
- **Diagnosticar 'en qué Python estoy' con `sys.executable` y 'qué proceso soy' con `os.getpid()`, desde el propio Python en vez de adivinar por el prompt.** _(Documentación estándar de CPython (módulos sys y os); reflejo diario de cualquier ingeniero para depurar entornos.)_ — El (.venv) del prompt es la ÚNICA pista que da T4, y es falible (prompts personalizados, sesiones heredadas). `sys.executable` imprime la ruta absoluta real del binario que está corriendo tu código: prueba objetiva de si el venv está activo. Y `os.getpid()` hace innecesario el baile `ps aux | grep python` de T3 para hallar tu propio PID.
- **Reemplazar el patrón manual `ps aux | grep nombre` → copiar PID → `kill PID` por `pgrep -f nombre` y `pkill -f nombre`, que buscan por el comando completo y matan en un paso. (En Windows: `Get-Process python | Stop-Process`.)** _(Suite procps-ng de Linux; uso estándar en scripts de ops. El gotcha que corrige es clásico: `ps aux | grep python` también encuentra al propio grep en su salida.)_ — Ahorra el ciclo copiar-pegar-PID en cada iteración del lab y evita el falso positivo del grep que se ve a sí mismo —un desconcierto típico de principiante. En tiempo de ejecución convierte tres comandos frágiles en uno robusto.
- **Manejar SIGTERM en Python con el módulo `signal` para cierre limpio (guardar estado, cerrar archivos) —el 'kill educado' de T3 visto desde dentro del proceso. Y saber que SIGKILL (kill -9) NO puede capturarse, confirmando en carne propia lo que T3 solo afirma.** _(Señales POSIX (TLPI, cap. de signals); patrón estándar en servidores y contenedores (Docker envía SIGTERM antes de SIGKILL al detener).)_ — Cierra el bucle entre 'observar señales desde fuera' (lo único que hace T3) y 'reaccionar a ellas desde dentro'. El alumno DEMUESTRA por qué SIGTERM es negociable y SIGKILL no: el handler corre con kill, se ignora con kill -9.
- **La respuesta pythónica al bug de 'variable con espacios sin comillas': nunca construir strings de shell; pasar una LISTA de argumentos a subprocess.run(...) (shell=False es el default), lo que elimina el word-splitting por diseño.** _(Documentación de subprocess de Python + guía de seguridad (evitar shell=True es la recomendación oficial contra inyección de comandos).)_ — T5 enseña el bug (`rm $nombre` parte 'mi archivo' en dos) y su parche en bash (comillas). El salto de nivel es entender que en Python el problema simplemente no existe si pasas una lista: cada elemento es un argumento, espacios incluidos. Conecta el criterio 'bash vs Python' del desafío de T5 con una razón técnica concreta.
- **El 'modo estricto de Bash' completo: `set -euo pipefail` + `IFS=$'\n\t'` en la cabecera del script. El IFS al inicio del archivo hace que la división de palabras solo ocurra en saltos de línea y tabs, no en espacios —blindando contra el mismísimo bug que T5 demuestra.** _(Aaron Maxwell, 'Use the Unofficial Bash Strict Mode (Unless You Looove Debugging)'; adoptado ampliamente en scripts de producción.)_ — T5 ya introduce `set -euo pipefail` pero se detiene ahí. Añadir la línea IFS convierte el 'ten cuidado de poner comillas' (frágil, depende de la disciplina humana) en una defensa estructural del script entero. Enseña que la robustez se diseña en la cabecera, no se recuerda en cada variable.
- **Atajos de historial y navegación que un practicante usa cientos de veces al día: `!!` (repite el último comando), `sudo !!` (repítelo con sudo), `!$` (último argumento del comando previo), Ctrl-R (búsqueda inversa en el historial), y `cd -` (vuelve al directorio anterior) + `pushd`/`popd` (pila de directorios).** _(Expansión de historial de Bash y builtins de navegación; enseñados explícitamente en Missing Semester del MIT (Lecciones 1 y 5).)_ — T2 hace del 'me perdí → pwd/cd' el reflejo central; `cd -` y pushd/popd son la herramienta exacta para reorientarse sin re-teclear rutas largas. `!$` y Ctrl-R eliminan el retecleo y copiar-pegar que ralentizan a todo principiante en tiempo de ejecución.

**Temas nuevos sugeridos:**

- **Streams estándar y redirección de errores (stdout, stderr, stdin, 2>, 2>&1, /dev/null)** — T5 enseña redirección de stdout (>, >>) pero nunca revela que existe un canal separado para errores. Es un pilar del modelo Unix ausente: sin él el alumno no entiende por qué `comando > log.txt` sigue mostrando errores en pantalla, ni cómo silenciarlos (2>/dev/null) o fusionarlos (2>&1). Lab corto (categoría A) que completa T5. _(fuente: The Linux Programming Interface (descriptores 0/1/2, capítulo de File I/O) + Missing Semester MIT 'Data Wrangling' (uso intensivo de stderr/stdout en tuberías).)_
- **Procesamiento de texto en la terminal: grep, find, sort, uniq, wc, cut (data wrangling)** — El pipe único de T5 (`ls | grep`) no representa la habilidad de shell de mayor apalancamiento real. Encadenar filtros de texto es exactamente lo que la referencia mundial trata como columna vertebral. Es el tema donde el módulo más se aleja del nivel MIT pese a que T5 promete 'componer el sistema'. _(fuente: Missing Semester MIT, Lección 4 'Data Wrangling' (sed/awk/sort/uniq/grep en tuberías con propósito real).)_
- **Control de trabajos: procesos en segundo plano (&, Ctrl-Z, jobs, fg, bg, nohup/disown)** — T3 cubre señales pero omite su compañero natural. El miniLab de T3 obliga a abrir tres terminales para correr tres procesos —el problema que `comando &` resuelve. Sin job control el alumno no sabe lanzar/suspender/reanudar procesos propios ni dejar uno corriendo tras cerrar sesión (nohup). _(fuente: Missing Semester MIT 'Command-line Environment' (job control junto a señales) + TLPI (grupos de procesos y control de terminal).)_
- **El PATH y cómo el shell encuentra un comando (which/where, variables de entorno, echo $PATH)** — T1 exige marcar 'Add Python to PATH' y hasta pregunta 'por qué es tan importante' sin haber explicado nunca qué es el PATH ni cómo el shell resuelve un ejecutable. Se pide criterio sobre un concepto no formalizado, contra la métrica 21 (intuición antes del término). Un lab de PATH cierra ese hueco y da el modelo que hace comprensible TODO lo demás (venv, comandos no encontrados). _(fuente: Missing Semester MIT, Lección 1 'Course overview + the shell' (resolución de comandos vía PATH como concepto fundacional).)_

### N1-M6 · Redes y APIs (T1-T6, Días 37-48) — clasificado B, cierre "B-M6"

**Veredicto:** necesita-trabajo

Módulo con una base pedagógica excelente y honestamente cercana al nivel mundial: progresión limpia (dos máquinas se entienden → contrato/confianza → frontera de datos hostil → fallar bien → auth → límites), citas reales y textuales (MDN para 401/403 y 429, Google SRE para backoff, Berkeley CS168 para la analogía postal de routers, Harvard CS50 para GET vs POST), misconceptions bien elegidas por tema, y el patrón scaffold-luego-retirar (retos sin starter donde el alumno decide el orden). Para un alumno desde cero es sólido y se defiende. PERO no llega a "mundial-listo" por un hueco central: todo el módulo enseña HTTP contra un cliente SIMULADO (api_get) y nunca hace que el alumno use requests real. Faltan las tres idiomas que las propias docs de requests marcan como obligatorias en producción — timeout=, raise_for_status(), y Session — y falta el modelo de que un fallo de red REAL lanza una excepción (Timeout/ConnectionError), no un status_code. Además T4 cita textualmente "randomized exponential backoff" de Google SRE pero el código solo enseña 2**intento SIN jitter, contradiciendo su propia fuente. Con esos arreglos el módulo sí competiría con CS144/MDN/requests docs.

**Gaps:**

- [alta] **M6.T2 y M6.T4/T5/T6 (uso de requests real)** — El alumno nunca escribe una llamada real con la librería requests. Todo es api_get simulado. Faltan las tres idiomas que las docs oficiales de requests marcan como esenciales: (1) el parámetro timeout= —las docs dicen literalmente 'Nearly all production code should use this parameter in nearly all requests; failure to do so can cause your program to hang indefinitely'—; (2) response.raise_for_status() para convertir 4xx/5xx en excepciones; (3) requests.get(url, params={...}, headers={...}, json={...}) con kwargs reales en vez de concatenar strings en la URL. _(por que: El estándar exige 'pasar una entrevista técnica difícil apoyándose solo en este tema'. Un alumno que termina M6 sabe el modelo mental pero no puede hacer una petición autenticada real ni evitar que su programa se cuelgue para siempre por falta de timeout. Es el gap más grande frente a las docs de requests.)_
- [media] **M6.T4 (backoff exponencial sin jitter)** — El MCQ cita textualmente Google SRE: 'Always use randomized exponential backoff', pero calcular_espera(intento) y reintentar_con_backoff solo devuelven 2**intento, SIN ninguna aleatorización. El código enseña la versión incompleta de la misma idea que la fuente dice que es incorrecta. _(por que: Es una contradicción interna entre la cita y el código. El backoff sin jitter causa el 'thundering herd': todos los clientes reintentan en el mismo instante y vuelven a tumbar el servicio que se recuperaba. Es exactamente el problema que la aleatorización resuelve, y la razón por la que AWS/Google lo exigen.)_
- [media] **M6.T4 (fallo de red = excepción, no status)** — El módulo modela TODOS los fallos como status_code o como strings ('timeout','conexion'). En requests real, un fallo de DNS, un timeout o una conexión rechazada LANZAN una excepción (requests.exceptions.Timeout, ConnectionError) antes de que exista cualquier status_code. No hay un solo try/except alrededor de una llamada de red enseñando esto. _(por que: Un principiante que solo vio el modelo simulado asumirá que puede leer r.status_code siempre; en la realidad su programa reventará con una excepción no capturada en el primer timeout. Es una brecha conceptual entre la simulación y el mundo real.)_
- [media] **M6 (métrica 6 de DOC-STD-01: lectura de código ajeno real)** — DOC-STD-01 métrica 6 exige leer 'código real de un repositorio real, no un ejemplo inventado'. El módulo cita texto de docs (MDN, SRE) pero no incluye ni un fragmento de código real (p.ej. de la librería requests, de un cliente de Stripe, o de un SDK) para que el alumno lo lea y critique. _(por que: Es una métrica de aceptación nombrada explícitamente en el estándar; sin al menos un ejercicio de lectura de código real, el módulo no cumple una de las 22 condiciones.)_
- [media] **M6.T4/T6 (amplitud de status codes)** — Solo se enseñan 200, 401, 403, 404, 429 y la familia 5xx. Faltan códigos que un consumidor de API real encuentra constantemente: 201 Created y 204 No Content (respuestas de POST/DELETE exitosos), 301/302/307 redirecciones (¡requests las sigue por defecto — gotcha real!), 400 vs 422 (validación), y 409 Conflict. La clase 3xx completa está ausente. _(por que: El alumno concluirá que 'éxito = 200' y se confundirá cuando un POST devuelva 201 o cuando requests siga silenciosamente una redirección. MDN HTTP status trata estas clases como fundamentales.)_
- [baja] **M6.T2 (métodos HTTP más allá de GET/POST)** — Solo GET y POST se enseñan con profundidad. PUT, PATCH y DELETE aparecen mencionados de pasada en T6 pero nunca se practica su semántica (safe vs idempotent, qué verbo para qué operación CRUD). No hay una tabla/ejercicio del cuadro de métodos de MDN. _(por que: La distinción safe/idempotent de los verbos es justo lo que T6 necesita para justificar por qué DELETE no requiere idempotency key y POST sí — pero esa base nunca se construye formalmente, así que T6 la asume.)_

**Trucos de experto a agregar:**

- **Reutilizar una requests.Session en vez de llamar a requests.get() suelto: la Session mantiene un pool de conexiones (HTTP keep-alive vía urllib3), así que reusa la misma conexión TCP+TLS en peticiones sucesivas al mismo host en vez de rehacer el handshake cada vez.** _(Documentación oficial de requests, sección 'Session Objects' (idiom estándar de la librería; el propio README lo recomienda para peticiones repetidas al mismo host).)_ — En tiempo de ejecución, evitar el handshake TCP+TLS por petición reduce la latencia de forma dramática cuando el alumno hace muchas llamadas al mismo API (justo el caso del ejercicio de 'diagnosticar varios servicios' y de paginación). Es el primer salto de 'funciona' a 'funciona rápido'.
- **Las dos líneas que nunca deben faltar: timeout= en CADA petición, y r.raise_for_status() justo después. timeout evita que el programa se cuelgue para siempre; raise_for_status convierte 4xx/5xx en una excepción en una sola línea en vez de un if manual.** _(Documentación oficial de requests ('Nearly all production code should use timeout in nearly all requests') y patrón estándar de la comunidad Python.)_ — El error #1 de principiantes con requests es un programa que se congela indefinidamente porque el servidor nunca responde y no había timeout. raise_for_status ahorra escribir la escalera de if status>=400 a mano y hace explícito el fallo en el punto exacto.
- **Full Jitter: la espera del reintento no es 2**intento fijo, sino un valor aleatorio uniforme entre 0 y ese tope: random.uniform(0, min(cap, base * 2**intento)). El azar 'descorrelaciona la manada' y evita que todos los clientes reintenten en el mismo milisegundo.** _(Marc Brooker, 'Exponential Backoff And Jitter', AWS Architecture Blog (2015) — la fórmula 'Full Jitter' hoy está incorporada en todos los SDK de AWS. Complementa exactamente la cita de Google SRE que el módulo ya usa.)_ — Convierte la lección de T4 de la versión incompleta (2**intento a secas, que causa thundering herd) a la que la industria realmente usa. El alumno entiende que el valor de reintentar bien no es solo 'esperar más' sino 'esperar un tiempo distinto que los demás'.
- **División entera para obtener la 'clase' del status en una sola operación: status // 100. 200//100==2 (éxito), 404//100==4 (cliente), 503//100==5 (servidor). Reemplaza tres comparaciones de rango por una resta mental.** _(Idiom pragmático muy extendido en código de clientes HTTP y en soluciones de competitive programming (aritmética entera para clasificar en cubetas); aparece en implementaciones reales de manejo de respuestas.)_ — El módulo repite el patrón 'if 500<=status<600 ... elif 400<=status<500' en T1, T4, T5 y T6. status//100 lo colapsa a una comparación limpia, menos propensa a errores de límite (¿era < o <=?), y hace el código más legible.
- **Usar el enum de la stdlib http.HTTPStatus en vez de números mágicos: HTTPStatus.NOT_FOUND == 404, y desde Python 3.12 los propios estados traen predicados de categoría: HTTPStatus(status).is_success / .is_client_error / .is_server_error.** _(Biblioteca estándar de Python, módulo http (HTTPStatus desde 3.5; propiedades is_success/is_client_error/is_server_error añadidas en Python 3.12).)_ — Elimina los números mágicos que el módulo usa por todos lados y documenta la intención en el propio código (HTTPStatus.TOO_MANY_REQUESTS se lee solo). Los predicados .is_* reemplazan las comparaciones de rango con una API oficial y a prueba de errores de límite.
- **Generar la idempotency key con uuid.uuid4() en el CLIENTE, una por operación real, y reusar exactamente esa misma key en cada reintento de esa operación. Es como Stripe implementa reintentos seguros de cobros.** _(Documentación de la API de Stripe (Idempotent Requests): el cliente envía un header Idempotency-Key con un UUID v4; el servidor recuerda la key ~24h y devuelve el resultado original si se repite.)_ — El módulo usa keys hardcodeadas ('key-abc'). uuid4() muestra la práctica real: unicidad garantizada sin coordinación central, de modo que un reintento tras un timeout (donde el cliente no sabe si el cobro pasó) nunca duplica el cargo. Cierra el laboratorio de pagos idempotentes con el patrón que usa la industria.

**Temas nuevos sugeridos:**

- **M6.T2.5 — requests de verdad: timeout, raise_for_status, Session, headers y json=** — Hueco conceptual real: el módulo enseña el modelo mental de HTTP con un cliente simulado pero nunca la librería que el alumno usará el resto de su vida profesional. Un día dedicado a la API real de requests (peticiones GET/POST con params=, headers=, json=; el timeout obligatorio; raise_for_status; y Session con keep-alive) cierra la brecha entre 'entiendo HTTP' y 'sé consumir un API'. Encaja natural entre T2 (contrato) y T3 (frontera de datos). _(fuente: Documentación oficial de requests (Quickstart, Advanced Usage / Session Objects, y la advertencia sobre timeout).)_
- **M6.T4.5 — Cuando la red lanza, no responde: excepciones de conexión y timeout** — El módulo entero modela fallos como status_code, pero en la realidad DNS caído, timeout y conexión rechazada lanzan excepciones (requests.exceptions.Timeout, ConnectionError, RequestException) antes de que exista status alguno. Sin esto el alumno cree que siempre puede leer r.status_code y su programa reventará en el primer fallo real. Medio día conecta la 'clasificación de fallos' de T4 con el árbol de excepciones real de requests y el try/except correcto. _(fuente: requests.exceptions (jerarquía RequestException → ConnectionError/Timeout/HTTPError) en las docs de requests; y el modelo de fallos de red de Stanford CS144 (pérdida, retransmisión, timeout).)_

**Trucos de experto a agregar:**

- **Usar la conexion como context manager: 'with con:' hace COMMIT si el bloque termina bien y ROLLBACK automatico si salta una excepcion. Reemplaza todo el patron manual try/except + commit/rollback que el modulo enseña.** _(Documentacion oficial de Python (sqlite3): 'Connection objects can be used as context managers that automatically commit or rollback transactions.' Es el idiom pythonico canonico.)_ — Elimina la clase de bug mas comun en transacciones: olvidar el rollback en el except o el commit en el camino feliz. El alumno escribe atomicidad correcta con 1 linea en vez de 5, y nunca deja un cambio a medias. Nota: 'with con:' NO cierra la conexion, solo gestiona la transaccion.
- **Asignar con.row_factory = sqlite3.Row para acceder a las columnas por nombre (fila['titulo']) en vez de por indice numerico fragil (fila[1]).** _(Documentacion oficial de Python (sqlite3.Row). Es la practica estandar en codigo de produccion con sqlite3.)_ — Todo el modulo accede con indices posicionales (cur.fetchone()[0]), que se rompen silenciosamente en cuanto cambia el orden de columnas en el SELECT. Con sqlite3.Row el codigo es autoexplicativo y resistente a cambios de esquema — la diferencia entre codigo de junior y de senior (metrica 5 del estandar).
- **UPSERT con INSERT ... ON CONFLICT(col) DO UPDATE SET ... = excluded.col : inserta si no existe, actualiza si ya existe, en UNA sola sentencia atomica. Reemplaza el patron 'SELECT primero, luego decidir INSERT o UPDATE'.** _(Documentacion oficial de SQLite (clausula UPSERT, disponible desde SQLite 3.24.0, 2018). Sintaxis heredada de PostgreSQL.)_ — Elimina la condicion de carrera y el codigo de dos pasos (SELECT + rama). La palabra clave 'excluded' referencia la fila que se intento insertar, permitiendo acumular (cantidad + excluded.cantidad). Conecta directo con el ejercicio registrar_usuarios_atomico, dando la alternativa profesional al try/except IntegrityError.
- **Regla del prefijo izquierdo (leftmost-prefix): un indice compuesto en (a, b, c) sirve para consultas que filtran por a, por (a,b) o por (a,b,c) — pero NO para una que filtre solo por b o solo por c. Diseña el orden de columnas del indice segun tus consultas mas frecuentes.** _(Principio de optimizacion documentado en 'Use The Index, Luke' (Markus Winand) y valido en SQLite, PostgreSQL y MySQL. Clasico de entrevistas de rendimiento.)_ — El modulo enseña a CREAR un indice multi-columna pero no cuando SE USA. Con esta regla el alumno diseña UN indice que sirve a varias consultas en vez de crear uno por consulta (que ralentiza escrituras). Verificable con el mismo EXPLAIN QUERY PLAN que ya domina: ve SEARCH cuando filtra por el prefijo, SCAN cuando filtra por una columna interior.

Es EL idiom para auditar unicidad antes de poner una restriccion UNIQUE.** _(Idiom estandar de SQL de auditoria de datos; pregunta clasica de entrevistas ('encuentra los emails repetidos'). Aplica el HAVING que el modulo ya enseña.)_ — Da un uso real e inmediato a HAVING (que en el modulo solo aparece en un ejercicio abstracto de paises). El alumno aprende a diagnosticar por que un ALTER TABLE ... ADD UNIQUE falla: primero encuentra los duplicados que lo impiden. Conecta deteccion de problemas con diseño de esquema (T4/T6).
- **Envolver muchos INSERT en UNA sola transaccion (executemany + un solo commit, o 'with con:'). En SQLite cada commit implicito fuerza un fsync a disco; agrupar miles de inserciones en una transaccion es tipicamente 100x-1000x mas rapido.** _(SQLite FAQ oficial ('INSERT is really slow - I can only do few dozen INSERTs per second'): la causa es un fsync por transaccion; la solucion es agrupar en BEGIN...COMMIT. Trampa de rendimiento clasica.)_ — Enseña que la lentitud percibida de una base de datos casi nunca es la base — es el patron de commit. El alumno mide la diferencia con sus propios ojos y aprende que 'insertar 10000 filas es lento' tiene una causa concreta y una solucion de una linea. Refuerza el concepto de transaccion de T3 con una motivacion de rendimiento tangible.
- **Anti-join para encontrar filas SIN pareja: LEFT JOIN ... WHERE tabla_derecha.id IS NULL devuelve exactamente las filas de la izquierda que no tienen correspondencia. Es la forma de responder 'que autores no tienen ningun libro' o 'que huerfanos quedaron'.** _(Patron estandar de SQL (anti-join); equivalente a NOT EXISTS. Aparece en CS186 y en todo material de JOINs. Combina el LEFT JOIN y el IS NULL que faltan articulados en el modulo.)_ — El modulo enseña LEFT JOIN (para no perder al que tiene cero) pero no el paso siguiente: usar el NULL resultante como filtro para AISLAR a los que no tienen pareja. Es justo la consulta que detectaria los libros huerfanos del gotcha de PRAGMA foreign_keys de T6 — cierra el circulo entre T2 y T6.

Convertir a set lo vuelve O(n).
- **@dataclass para clases de datos sin escribir __init__/__repr__/__eq__** _(Modulo dataclasses de la stdlib, PEP 557 (Python 3.7). Feature oficial.)_ — Genera constructor, repr legible y comparacion por igualdad automaticamente. Elimina decenas de lineas de boilerplate propensas a error.
- **@property para exponer un metodo como atributo calculado (getter)** _(Built-in property de Python. Idiom oficial para encapsulacion sin getters/setters estilo Java.)_ — Permite empezar con un atributo publico y luego anadir logica sin cambiar la interfaz (no rompe el codigo que usa obj.area).
- **enum.Enum para constantes con nombre en vez de strings o numeros 'magicos'** _(Modulo enum de la stdlib, PEP 435 (Python 3.4). Feature oficial.)_ — Evita errores de tipeo con strings ('activo' vs 'activa') y da autocompletado. Los valores invalidos fallan al construirse, no en silencio.
- **Window functions: ROW_NUMBER()/RANK() OVER (PARTITION BY ... ORDER BY ...)** _(SQL estandar (SQL:2003). Herramienta central de analistas de datos y entrevistas.)_ — Numera/rankea filas dentro de grupos sin colapsarlos (a diferencia de GROUP BY). Resuelve 'top N por categoria' o 'ultimo registro por usuario' de forma limpia.
- **CTE con WITH para nombrar subconsultas y hacer consultas legibles** _(SQL estandar (Common Table Expression). Recomendado en toda guia de SQL avanzado para legibilidad.)_ — Descompone una consulta compleja en pasos con nombre en vez de subconsultas anidadas ilegibles. Un CTE puede reusarse y depurarse por partes.
- **EXPLAIN antes de optimizar + indice en columnas de WHERE/JOIN** _(Practica estandar de DBAs/ingenieros de datos. EXPLAIN existe en PostgreSQL, MySQL, SQLite.)_ — EXPLAIN muestra si la consulta hace un 'full table scan' (lento) o usa indice. Es el truco #1 de rendimiento: medir antes de adivinar.
- **git bisect: busqueda binaria en el historial para hallar el commit que rompio algo** _(Comando oficial de Git. Aplica binary search al historial de commits.)_ — Encuentra el commit culpable en O(log n) pruebas en vez de revisar todos los commits (O(n)). Ahorra horas de depuracion en historiales largos.
- **git reflog para recuperar commits 'perdidos' tras reset --hard o rebase** _(Comando oficial de Git. reflog registra todo movimiento de HEAD.)_ — Casi nada se pierde de verdad en Git: reflog lista los HEAD anteriores y permite volver a un commit huerfano. Red de seguridad ante errores destructivos.
- **curl -v y mnemotecnia de codigos HTTP (2xx ok, 3xx redirige, 4xx tu culpa, 5xx del servidor)** _(curl es estandar; la mnemotecnia de familias de codigos HTTP es folclore muy difundido (no de un autor unico).)_ — Permite depurar redes/APIs desde la terminal sin escribir codigo. Saber que 4xx = error del cliente y 5xx = del servidor orienta el diagnostico al instante.

**Temas nuevos sugeridos:**

- **El reflejo de la stdlib: no reinventes la rueda (collections, itertools, functools)** — Es el objetivo explicito del curso: que el alumno experto no reimplemente a mano lo que la libreria estandar ya hace optimizado en C. Reune Counter, defaultdict, deque, accumulate, groupby, combinations y lru_cache como primer reflejo antes de escribir logica manual. _(fuente: Documentacion oficial de Python (modulos collections/itertools/functools); libro 'Effective Python' de Brett Slatkin; charla 'Beyond PEP 8'.)_
- **Patrones de arrays y strings: two pointers, sliding window y prefix sums** — Estos 3-4 patrones de competitive programming resuelven la mayoria de problemas de arrays de entrevistas y competencias, bajando de O(n^2) a O(n). Presentarlos como patrones nombrados y reconocibles le da al alumno una caja de herramientas que un experto aplica en segundos. _(fuente: USACO Guide (usaco.guide/silver/two-pointers); blogs de Codeforces (entry/144990); tradicion de olimpiadas de programacion.)_
- **Big-O de operaciones built-in: la tabla que debes memorizar (dict vs list vs set)** — La formula practica que evita el bug de rendimiento mas comun (buscar en lista dentro de bucle = O(n^2), list.pop(0) = O(n)). Las universidades top hacen memorizar esta tabla porque es la que decide dict vs list en el acto. _(fuente: Python Wiki TimeComplexity; cheat sheet de GeeksforGeeks 'Complexity Cheat Sheet for Python Operations'; MIT 6.006.)_
- **EAFP vs LBYL: la filosofia pythonica de manejo de errores** — Define el 'sabor' idiomatico de Python frente a un estilo defensivo importado de Java/C. Un alumno desde cero debe aprender por que try/except (o dict.get) es preferible a cadenas de if para comprobar antes. _(fuente: Glosario oficial de Python (entradas EAFP y LBYL); doc oficial del lenguaje.)_
- **Depurar sin adivinar: f'{x=}', breakpoint() e invariantes de bucle** — Combina atajos de depuracion modernos (f-string de debug, breakpoint del 3.7) con la tecnica de Dijkstra de invariantes de bucle para razonar correctitud. Da al alumno una forma sistematica de convencerse de que su codigo es correcto en vez de sembrar prints. _(fuente: Python 3.8 (especificador = en f-strings); PEP 553 (breakpoint); Dijkstra 'Notes on Structured Programming' (EWD249); paper SIGCSE 'Teaching loop invariants to beginners by examples'.)_
- **Git como red de seguridad: reflog, bisect y stash** — Ahorro de tiempo real diario y prevencion de perdida de trabajo. bisect convierte la caza de un bug en O(log n); reflog recupera commits que parecian perdidos; stash permite cambiar de contexto sin ensuciar el historial. Un principiante sin esto pierde horas y a veces datos. _(fuente: Documentacion oficial de Git (git-bisect, git-reflog, git-stash); guias practicas de DEV Community y DeployHQ.)_
